# 示例 UI 与后续优化

参考文件已从 kaiyuan2 的 `D:\Kaiyuan\UGRD\research\humanoid\G1_D部署（Windows系统）.pdf` 取回。示例并非独立桌面控制面板，而是由宇树具身智能平台、相机 WebRTC 页面和 PICO VR 页面组成的操作流程。

现有 UI 的主要状态是：

1. EAI 平台登录、设备白名单、移动机器人设备和任务创建；
2. 任务列表显示设备在线状态、采集进度和“开始采集”；
3. 三路相机分别通过 `60001/60002/60003` 页面检查；
4. PICO 通过 `8012` 页面进入 Virtual Reality，做房间标定并建立连接；
5. 入口脚本用 `R` 连接、`S` 开始/结束采集、`Q` 断开。

后续如果做本项目自己的控制台，第一版适合只聚合这些已有状态：

```text
┌──────────────────────────────────────────────────────────┐
│ G1-D 设备在线  DDS正常  Dex1正常  XR已连接  30 Hz       │
├───────────────────────┬──────────────────────────────────┤
│ 头部/腕部相机预览      │ 当前控制量                       │
│                       │ vx  vyaw  lift  waist_pitch      │
│                       │ 左/右臂接管  左/右夹爪开度       │
├───────────────────────┴──────────────────────────────────┤
│ Episode: 0012  ● REC  00:01:24  帧数/丢帧/磁盘余量      │
│ [建立连接] [开始/结束采集] [安全停止] [保存/丢弃]        │
└──────────────────────────────────────────────────────────┘
```

UI 必须明确显示控制源和冲突：官方 DDS 后端、SDK2 AgvClient bridge、R3 手柄三者只能有一个底盘/升降发布者。还应显示 XR `motion_ready`、最后指令时延、Dex1 状态反馈与看门狗是否触发。这些信息比单纯复制平台的任务列表更能降低现场数采失败率。

PDF 还记录了几项现场问题：PICO 到机器人可能有 4–5 秒延时；夹爪偶发断开；VR 页面可能闪退；EAI 平台可能显示设备离线。排查入口应直接链接或展示 `config.yaml`、agent 进程、相机服务、Dex1 systemd 日志和网络连通状态。
